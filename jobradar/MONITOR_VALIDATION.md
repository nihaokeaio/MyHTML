## 3. 本地运行与发布方案

已在本机现有 PowerShell 7、项目 .venv 下执行：

```powershell
pwsh -NoProfile -File E:\Tools\MyHTML\scripts\run_jobradar.ps1
```

脚本按绝对项目路径运行，依次采集、正文/附件解析、生成增量摘要。批次使用 UUID；.jobradar-state/run.lock 防重叠；状态基线与日志保存在 .jobradar-state，不提交公开仓库。上游来源失败后不继续重复请求该来源历史正文。任一步失败，完整批次仍为退出码 1，成功数据和有告警的摘要照常保存。

发布准备：

```powershell
.\.venv\Scripts\python.exe scripts/prepare_jobradar_release.py --output scratch/monitor/release-final
```

仅打包 jobradar/jobs.json 与 jobradar/daily-summary.json。检查同批次 run_id/更新时间、26 小时新鲜度、至少有成功来源及正文、错误状态未被摘要掩盖，并输出 SHA256 清单。不会执行 git add、commit 或 push。

已用 scratch/monitor 下独立工作仓库及本地 bare 仓库模拟提交/推送到 codex/jobradar-monitor-validation，核对仅两个 JSON 文件，远端仅有该测试分支、没有 main。此处“远端”是本机目录，不是 GitHub。主仓库没有提交或分支改动；尚未进行真实 GitHub 测试分支推送、Actions 或 Pages 更新验证。

每天自动运行还需经用户确认完成：
1. 确定运行时间、Windows 用户、机器开机/唤醒与网络条件；本轮不创建任务。
2. 后续由用户确认配置任务计划程序，指定 PowerShell、脚本绝对路径及 .venv，并检查退出码和日志。锁残留需先确认无运行进程再人工恢复。
3. 确定唯一数据写入者；本地采集投入使用前，处理旧 GitHub Actions 定时采集，避免两个环境覆盖同一数据。
4. 若自动发布，先配置凭据保管方式及 GitHub 测试分支，仅允许发布上述两个数据文件；先在真实测试分支验证，再经用户决定如何更新 Pages 使用的数据分支。不得直接自动推送 main。
5. 确定采集失败/数据过期的提醒方式；目前只有退出码、摘要 health 和日志，没有邮件或其他通知。
6. 保留并备份增量基线；删除基线会改变首次发现语义。之后再做连续多日无人值守验收，本轮未声称长期稳定。
